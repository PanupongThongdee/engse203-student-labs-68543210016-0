## 1. ภาพรวม

```
+-------------------+       1:N       +------------------------+
|       users       | <-------------- |        requests        |
+-------------------+                 +------------------------+
| id (PK)           |                 | id (PK)                |
| name              |                 | requester_id (FK)      |
| department        |                 | request_type           |
| email (UNIQUE)    |                 | location               |
+-------------------+                 | details                |
                                      | priority               |
                                      | status                 |
                                      | created_at             |
                                      +------------------------+
```
---
**One-to-One (1:1):** ฝั่งละ 1 ตัวเลือก เช่น คน 1 คน มีบัตรประชาชน 1 ใบ

**One-to-Many (1:N):** ฝั่งหนึ่งมีได้หลายตัวเลือก (ใช้ในโปรเจกต์เรา) เช่น ผู้ใช้ 1 คน ส่งคำร้องได้หลายใบ

**Many-to-Many (M:N):** จับคู่ไขว้กันได้หลายตัวทั้งสองฝั่ง เช่น นักศึกษาหลายคน เรียนหลายวิชา (ต้องมีตารางกลางช่วยเชื่อม)

## 2. ทำไมต้องแยกเป็น 2 ตาราง

ในสัปดาห์ที่ 06–07 เราเคยเก็บข้อมูลชื่อผู้แจ้ง (`requesterName`) เป็นข้อความธรรมดา (String) รวมอยู่กับตารางคำร้องโดยตรง ซึ่งการออกแบบลักษณะนั้นก่อให้เกิดปัญหาสำคัญดังนี้:

1. **ปัญหาความซ้ำซ้อนของข้อมูล (Data Redundancy):** หากผู้ใช้คนหนึ่งส่งคำร้อง 10 คำร้อง ชื่อ อีเมล และสังกัดของคนๆ นั้นจะถูกบันทึกซ้ำๆ กันถึง 10 แถว ทำให้สิ้นเปลืองพื้นที่จัดเก็บข้อมูลโดยไม่จำเป็น
2. **ปัญหาความไม่สอดคล้องของข้อมูล (Data Anomaly) และการอัปเดตที่ยุ่งยาก:** หากผู้ใช้ (เช่น สมชาย) มีการเปลี่ยนแปลงข้อมูลส่วนตัว เช่น เปลี่ยนชื่อ หรือเปลี่ยนอีเมล หากเราเก็บข้อมูลแบบรวมเป็นตารางเดียว เราจะต้องตามไปแก้ไขข้อมูลในทุกๆ แถวของคำร้องที่สมชายเคยส่งเข้ามาทั้งหมด ซึ่งหากแก้ไขไม่ครบถ้วนจะทำให้ข้อมูลเกิดความขัดแย้งกันเอง (เช่น แถวเก่าเป็นชื่อเดิม แถวใหม่เป็นชื่อที่เปลี่ยนแล้ว)

**การแก้ปัญหาด้วยการแยกตาราง:**
การแยกตารางออกเป็น `users` (เก็บข้อมูลผู้ใช้) และ `requests` (เก็บข้อมูลคำร้อง) โดยเชื่อมโยงกันผ่าน Foreign Key (`requester_id`) ช่วยแก้ปัญหาดังกล่าวได้อย่างสมบูรณ์ กล่าวคือ **"ถ้าสมชายเปลี่ยนชื่อ เราจะต้องแก้ไขข้อมูลที่ตาราง `users` เพียงแค่แถวเดียวเท่านั้น"** ข้อมูลในตาราง `requests` ทั้งหมดจะสะท้อนชื่อใหม่ของสมชายทันทีผ่านกระบวนการ JOIN ข้อมูลในระบบฐานข้อมูล

## 3. รายละเอียดตาราง

### ตารางที่ 1: `users` (ข้อมูลผู้ใช้งาน)
| คอลัมน์ | ชนิดข้อมูล (Type) | ข้อกำหนด (Constraints) | เหตุผลที่เลือกใช้ชนิดและข้อกำหนดนี้ |
| :--- | :--- | :--- | :--- |
| `id` | INT / SERIAL | PRIMARY KEY, AUTO_INCREMENT | ใช้เป็นรหัสประจำตัวที่ไม่ซ้ำกันสำหรับผู้ใช้แต่ละคน เพื่อให้ระบบอ้างอิงและเชื่อมโยงข้อมูลกับตารางอื่นได้อย่างแม่นยำ |
| `name` | VARCHAR(100) | NOT NULL | ต้องการเก็บชื่อ-นามสกุลของผู้ใช้ โดยกำหนดความยาวสูงสุดที่เหมาะสมและบังคับว่าต้องมีค่าเสมอ (ห้ามว่าง) |
| `department` | VARCHAR(100) | NOT NULL | ระบุแผนกหรือสังกัดของผู้ใช้งาน เพื่อใช้ในการคัดแยกประเภทคำร้องตามหน่วยงาน |
| `email` | VARCHAR(150) | NOT NULL, UNIQUE | ใช้เป็นช่องทางติดต่อและชื่อบัญชีในการเข้าสู่ระบบ จึงต้องบังคับไม่ให้เป็นค่าว่าง (`NOT NULL`) และห้ามซ้ำกัน (`UNIQUE`) |

### ตารางที่ 2: `requests` (ข้อมูลคำร้องขอรับบริการ)
| คอลัมน์ | ชนิดข้อมูล (Type) | ข้อกำหนด (Constraints) | เหตุผลที่เลือกใช้ชนิดและข้อกำหนดนี้ |
| :--- | :--- | :--- | :--- |
| `id` | INT / SERIAL | PRIMARY KEY, AUTO_INCREMENT | รหัสประจำคำร้อง (Request ID) เพื่อให้แต่ละคำร้องมีตัวระบุที่ไม่ซ้ำกัน |
| `requester_id` | INT | FOREIGN KEY (`users.id`), NOT NULL | ใช้เชื่อมโยงว่าคำร้องนี้ใครเป็นผู้ส่ง โดยอ้างอิงไปยังรหัสผู้ใช้ในตาราง `users` และบังคับว่าทุกคำร้องต้องมีผู้รับผิดชอบเสมอ |
| `request_type` | VARCHAR(50) | NOT NULL, CHECK | ประเภทของคำร้อง (เช่น แจ้งซ่อม, ขอความช่วยเหลือ) กำหนดให้ตรวจสอบค่าที่ยอมรับได้ผ่าน CHECK constraint |
| `location` | VARCHAR(150) | NOT NULL | สถานที่เกิดเหตุหรือสถานที่รับบริการ เพื่อให้เจ้าหน้าที่เดินทางไปปฏิบัติงานได้อย่างถูกต้อง |
| `details` | TEXT | NULL | รายละเอียดอธิบายปัญหาเพิ่มเติม ซึ่งอาจมีความยาวมาก จึงใช้ชนิดข้อมูล `TEXT` |
| `priority` | VARCHAR(20) | NOT NULL, DEFAULT 'Normal' | ระดับความสำคัญของงาน (เช่น Low, Normal, High, Urgent) พร้อมกำหนดค่าเริ่มต้นเป็น 'Normal' |
| `status` | VARCHAR(20) | NOT NULL, DEFAULT 'Pending' | สถานะการดำเนินการ (เช่น Pending, In Progress, Completed) เพื่อติดตามความคืบหน้า |
| `created_at` | TIMESTAMP | NOT NULL, DEFAULT CURRENT_TIMESTAMP | บันทึกเวลาที่สร้างคำร้องโดยอัตโนมัติ เพื่อประโยชน์ในการจัดลำดับเวลาทำงาน |

## 4. เหตุผลของการเลือกชนิดและข้อกำหนด

1. **ทำไม `users.id` กับ `requests.id` ถึงออกแบบให้เหมาะสมกับบริบท:**
   - ทั้งสองตารางใช้ชนิดข้อมูลตัวเลข (`INT` พร้อมคุณสมบัติ `AUTO_INCREMENT` หรือ `SERIAL`) เป็น Primary Key เนื่องจากข้อมูลตัวเลขมีการประมวลผลและการเปรียบเทียบที่รวดเร็วที่สุดโดยระบบฐานข้อมูล เหมาะสำหรับการทำ Indexing และการทำ Foreign Key Joint ในตารางขนาดใหญ่

2. **ทำไมต้องมี CHECK constraint ทั้งที่ API ก็ตรวจข้อมูล (Validation) อยู่แล้ว:**
   - **Data Integrity (ความถูกต้องของข้อมูลในระดับฐานข้อมูล):** แม้ว่าฝั่ง Frontend หรือ Backend API จะมี Validation ตรวจสอบข้อมูลก่อนส่งเข้ามาแล้ว แต่ฐานข้อมูลคือด่านสุดท้าย (Last Line of Defense) หากมีการเชื่อมต่อฐานข้อมูลโดยตรงจากสคริปต์อื่น, การทำ Database Migration, หรือข้อผิดพลาดทางโค้ดที่ทำให้ผ่าน API มาได้ CHECK constraint จะช่วยป้องกันไม่ให้ข้อมูลที่ผิดรูปแบบ (เช่น ระดับความสำคัญเป็นค่ามั่วๆ หรือสถานะที่ไม่ถูกต้อง) ถูกบันทึกกลายขยะในระบบฐานข้อมูลได้

## 5. ตัวอย่างการใช้ JOIN

ตัวอย่างคำสั่ง SQL สำหรับดึงข้อมูลคำร้องทั้งหมด พร้อมทั้งดึงชื่อและอีเมลของผู้ใช้งานที่เป็นเจ้าของคำร้องนั้นมาแสดงร่วมกัน:

```sql
SELECT u.name, u.department, r.request_type, r.location, r.details
FROM requests r
JOIN users u ON u.id = r.requester_id
WHERE u.department LIKE '%ไฟฟ้า%'
ORDER BY u.id;
```

**ผลลัพธ์**

| name | department | request_type | location | details |
|---|---|---|---|---|
| ปริวัตต์ เทพอินทร์ | วิศวกรรมไฟฟ้า | ขอใช้อุปกรณ์ | ห้องประชุม 2 | ขอยืมโปรเจกเตอร์สำหรับนำเสนอโครงงาน |
