# API Contract — Campus Service Request API

**เวอร์ชัน:** 2.0.0 · **Base URL:** `http://localhost:3001`
**รูปแบบข้อมูล:** JSON (`Content-Type: application/json`)

> **API Contract คืออะไร** — ข้อตกลงระหว่างคนทำ front-end กับคนทำ back-end
> ว่าจะคุยกันด้วย endpoint อะไร ส่งอะไรไป ได้อะไรกลับ
> มีไว้เพื่อให้สองฝั่ง**ทำงานคู่ขนานกันได้** โดยไม่ต้องรอกัน

---

## โครงสร้างข้อมูล Request

| field | ชนิด | คำอธิบาย | ตัวอย่าง |
|---|---|---|---|
| `id` | string | รหัสคำร้อง · ขึ้นต้นด้วย `REQ-` · เซิร์ฟเวอร์สร้างให้ | `"REQ-001"` |
| `requesterName` | string | ชื่อผู้แจ้ง · อย่างน้อย 2 ตัวอักษร | `"สมชาย ใจดี"` |
| `requestType` | string | ประเภท · 1 ใน 4 ค่าที่กำหนด | `"แจ้งซ่อม"` |
| `location` | string | สถานที่ · ห้ามว่าง | `"ห้องปฏิบัติการ 301"` |
| `details` | string | รายละเอียด · อย่างน้อย 10 ตัวอักษร | `"เครื่องปรับอากาศไม่ทำงาน"` |
| `priority` | string | `"normal"` หรือ `"urgent"` | `"urgent"` |
| `status` | string | `"pending"` · `"in-progress"` · `"completed"` | `"pending"` |

**ค่าที่ยอมรับของ `requestType`** — `แจ้งซ่อม` · `บริการบัญชีผู้ใช้` · `ขอใช้อุปกรณ์` · `อื่น ๆ`

## Endpoints

| Method | Endpoint | คำอธิบาย | Request body | สำเร็จ | ผิดพลาด |
|---|---|---|---|---|---|
| `GET` | `/api/requests` | ดูคำร้องทั้งหมด | — | `200` + array | — |
| `GET` | `/api/requests?status=` | กรองตามสถานะ | — | `200` + array | — |
| `GET` | `/api/requests/:id` | ดูคำร้องใบเดียว | — | `200` + object | `404` ไม่พบ |
| `POST` | `/api/requests` | สร้างคำร้องใหม่ | Request (ไม่ต้องมี `id`, `status`) | `201` + object ที่สร้าง | `400` ข้อมูลไม่ถูกต้อง |
| `PUT` | `/api/requests/:id` | เปลี่ยนสถานะ | `{ "status": "..." }` | `200` + object ที่แก้แล้ว | `400` สถานะผิด · `404` ไม่พบ |
| `DELETE` | `/api/requests/:id` | ลบคำร้อง | — | `204` ไม่มี body | `404` ไม่พบ |

## ตัวอย่างการเรียกใช้

### GET /api/requests

```http
GET /api/requests HTTP/1.1
Host: localhost:3001
```

```json
[
  {
    "id": "REQ-001",
    "requesterName": "สมชาย ใจดี",
    "requestType": "แจ้งซ่อม",
    "location": "ห้องปฏิบัติการ 301",
    "details": "เครื่องปรับอากาศไม่ทำงานตั้งแต่เช้า",
    "priority": "urgent",
    "status": "pending"
  }
]
```

### POST /api/requests

```http
POST /api/requests HTTP/1.1
Content-Type: application/json

{
  "requesterName": "สุภาวดี รักเรียน",
  "requestType": "ขอใช้อุปกรณ์",
  "location": "ห้องประชุม 2",
  "details": "ขอยืมโปรเจกเตอร์สำหรับนำเสนอ",
  "priority": "normal"
}
```

**201 Created**

```json
{
  "id": "REQ-MTYOA3MX-YEX9",
  "requesterName": "สุภาวดี รักเรียน",
  "requestType": "ขอใช้อุปกรณ์",
  "location": "ห้องประชุม 2",
  "details": "ขอยืมโปรเจกเตอร์สำหรับนำเสนอ",
  "priority": "normal",
  "status": "pending"
}
```

**400 Bad Request** — เมื่อข้อมูลไม่ถูกต้อง

```json
{
  "error": "ข้อมูลคำร้องไม่ถูกต้อง",
  "details": [
    "ชื่อผู้แจ้งต้องมีอย่างน้อย 2 ตัวอักษร",
    "รายละเอียดต้องมีอย่างน้อย 10 ตัวอักษร"
  ]
}
```

### PUT /api/requests/:id

```http
PUT /api/requests/REQ-001 HTTP/1.1
Content-Type: application/json

{ "status": "in-progress" }
```

**200 OK** — คืนคำร้องที่อัปเดตแล้ว

### DELETE /api/requests/:id

**204 No Content** — ไม่มี body ส่งกลับ

## รูปแบบ Error

ทุก error ตอบเป็น JSON ที่มี field `error` เสมอ

```json
{ "error": "ข้อความที่ผู้ใช้ทั่วไปอ่านเข้าใจ" }
```

กรณี validation จะมี `details` เพิ่มมาเป็น array บอกว่าผิดตรงไหนบ้าง

| Status | เมื่อไหร่ | ฝั่งไหนผิด |
|---|---|---|
| `400` | ข้อมูลที่ส่งมาไม่ถูกต้อง | ผู้ใช้ |
| `404` | ไม่พบทรัพยากรที่ขอ | ผู้ใช้ |
| `500` | โค้ดเซิร์ฟเวอร์ผิดพลาด | เซิร์ฟเวอร์ |

> **ตอน production จะไม่ส่ง stack trace กลับไป** — เปิดเผยโครงสร้างภายในให้คนภายนอกเห็นไม่ได้

## CORS

API อนุญาตให้เรียกจาก origin ที่กำหนดใน `CORS_ORIGIN` เท่านั้น

```
Access-Control-Allow-Origin: http://localhost:5173
```

**ถ้าเรียกจาก origin อื่น** เบราว์เซอร์จะบล็อกก่อนที่โค้ดจะได้เห็น response — จะเห็น error ใน Console ว่าถูกบล็อกโดย CORS policy

> ⚠ CORS เป็นกลไกของ **เบราว์เซอร์** เท่านั้น · Postman และ curl ไม่ถูกบล็อก เพราะไม่ใช่เบราว์เซอร์

## Environment Variables

### ฝั่ง API (`api/.env`)

| ตัวแปร | ค่าเริ่มต้น | คำอธิบาย |
|---|---|---|
| `PORT` | `3001` | พอร์ตที่ API รับคำขอ |
| `CORS_ORIGIN` | `http://localhost:5173` | origin ที่อนุญาตให้เรียก |
| `NODE_ENV` | `development` | `production` จะเปลี่ยนรูปแบบ log และซ่อน stack trace |

### ฝั่ง Frontend (`frontend/.env.local`)

| ตัวแปร | ค่าเริ่มต้น | คำอธิบาย |
|---|---|---|
| `VITE_API_BASE_URL` | `http://localhost:3001` | ที่อยู่ของ API |

> **ต้องขึ้นต้นด้วย `VITE_`** ไม่งั้น Vite จะไม่ส่งค่าไปให้โค้ดฝั่งเบราว์เซอร์
> และ**ห้าม commit ไฟล์ `.env`** — ใช้ `.env.example` เป็นตัวอย่างแทน

## ① Data Model (โครงสร้างข้อมูลฐานข้อมูล)

ระบบใช้งานฐานข้อมูล SQLite โดยมีตารางหลัก 2 ตาราง ดังนี้ครับ:

### ตาราง `users`

เก็บข้อมูลผู้ใช้งานในระบบ

| คอลัมน์ | ชนิดข้อมูล | ข้อกำหนด | คำอธิบาย |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY, AUTOINCREMENT | รหัสประจำตัวผู้ใช้ มีการ create เลขอัตโนมัติ |
| `name` | TEXT | NOT NULL | ชื่อ-นามสกุลของผู้ใช้งาน ต้องบังคับใส่เพื่อระบุเจ้าของบัญชี |
| `department` | TEXT | NOT NULL | คณะแผนก ใช้คัดแยกนักศึกษาว่าอยู่ คณะไหน |
| `email` | TEXT | NOT NULL, UNIQUE | อีเมลติดต่อ ห้ามว่างและห้ามซ้ำ ใช้เป็นข้อมูลระบุตัวตนที่ไม่ซ้ำกัน |

### ตาราง `requests`

เก็บข้อมูลคำร้องขอรับบริการที่ผู้ใช้แจ้งเข้ามา

| คอลัมน์ | ชนิดข้อมูล | ข้อกำหนด | คำอธิบาย |
|---|---|---|---|
| `id` | TEXT | PRIMARY KEY | รหัสคำร้องแบบกำหนดรูปแบบเอง (เช่น `REQ-001`) เพื่อระบุลำดับคำร้องขอ |
| `requester_id` | INTEGER | NOT NULL, FOREIGN KEY → `users(id)` | เชื่อมความสัมพันธ์กับตาราง `users` เพื่อบังคับว่าทุกคำร้องต้องมีผู้แจ้งอยู่ในระบบจริง |
| `request_type` | TEXT | NOT NULL, CHECK | ประเภทของคำร้อง จำกัดให้เลือกเฉพาะค่าที่กำหนดไว้ ป้องกันข้อมูลผิดพลาด |
| `location` | TEXT | NOT NULL | สถานที่เกิดเหตุ/รับบริการ ห้ามเว้นว่าง เพื่อให้ทีมงานทราบจุดที่ต้องเข้าไปปฏิบัติงาน |
| `details` | TEXT | NOT NULL | รายละเอียดอธิบายปัญหา บังคับระบุเพื่อให้เข้าใจความต้องการและสาเหตุ |
| `priority` | TEXT | NOT NULL, DEFAULT | ระดับความเร่งด่วน ค่าเริ่มต้นคือ `normal` และ เรงด่วนคือ `urgent` |
| `status` | TEXT | NOT NULL, DEFAULT | สถานะของคำร้อง เช่น `pending`, `in-progress`, `completed` ควบคุมด้วย CHECK ให้เป็นไปตามขั้นตอนการทำงานจริง |
| `created_at` | TEXT | NOT NULL, DEFAULT | เวลาที่สร้างคำร้อง บันทึกอัตโนมัติด้วยฟังก์ชันเวลาปัจจุบัน เพื่อให้ตรวจสอบลำดับก่อน-หลังได้ |

## ② ข้อสังเกตเรื่องรูปแบบข้อมูล (Format Discrepancies)

โครงสร้างข้อมูลที่จัดเก็บในฐานข้อมูลจะไม่ตรงกับรูปแบบที่ API ส่งออก (Response) โดยมีเหตุผลดังนี้:

- **ในฐานข้อมูล**: จัดเก็บ `requester_id` (ที่เป็นตัวเลข Foreign Key) เพื่อความถูกต้องตามหลัก Database Normalization ป้องกันข้อมูลชื่อซ้ำซ้อน และจัดการความสัมพันธ์ได้ง่าย
- **ที่ API ส่งออก**: คืนค่าเป็น `requesterName` (ที่เป็นชื่อข้อความ String) แทน เนื่องจากฝั่ง Frontend และผู้ใช้งานจริงต้องการแสดงผลเป็นชื่อบุคคลโดยตรง ไม่ใช่รหัสไอดี
- **ตัวเชื่อมเบื้องหลัง**: ชั้น Service จะทำหน้าที่แปลงข้อมูลด้วยคำสั่ง SQL `JOIN` และใช้ Alias (`AS requesterName`) เพื่อดึงชื่อจริงจากตาราง `users` มาแสดงผลแทนที่ไอดีในชุดข้อมูล JSON ที่ส่งให้ Client เสมอ

## ③ พฤติกรรมของ POST ⭐ (สำคัญที่สุด)
พฤติกรรมหลัก: หากทำการส่งคำขอ POST ไปพร้อมกับ requesterName ที่ยังไม่มีอยู่ในระบบ ระบบฐานข้อมูลจะทำการสร้าง User (ผู้ใช้) ใหม่ให้อัตโนมัติทันที

ทำไมข้อนี้ถึงสำคัญมาก:
 
เป็นพฤติกรรมที่ผู้ใช้งานหรือผู้พัฒนาคนอื่นไม่สามารถคาดเดาได้จากการดูแค่ชื่อ `Endpoint` หรือ `Contract` ทั่วไปเพียงอย่างเดียว

หากไม่มีการระบุหรือเขียนอธิบายไว้ ผู้ที่นำ API ไปใช้งานต่ออาจจะไม่รู้ว่าการส่ง POST ข้อมูลเข้ามาอาจทำให้เกิดการสร้างข้อมูลผู้ใช้ใหม่ขึ้นมาเรื่อยๆ จนกลายเป็น "ผู้ใช้ขยะ" `(Spam/Trash Users)`ในระบบโดยไม่ตั้งใจ

หัวใจสำคัญของ Contract: สัญญาการใช้งาน (Contract) มีไว้เพื่อบอกในสิ่งที่เรา "เดาไม่ได้" จากตัว Endpoint ไม่ใช่แค่การคัดลอกรายชื่อ `Endpoint` มาแปะเฉยๆ
