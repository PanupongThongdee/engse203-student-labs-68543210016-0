## 1. SQL กับ NoSQL ต่างกันอย่างไร

| | SQL (SQLite) | NoSQL (MongoDB) |
|---|---|---|
| รูปแบบข้อมูล | ตาราง / แถว / คอลัมน์ | collection / document |
| โครงสร้าง | ตายตัว ทุกแถวมีคอลัมน์เหมือนกัน (schema บังคับ) | ยืดหยุ่น แต่ละ document มี field ต่างกันได้ |
| ความสัมพันธ์ | มี foreign key และ JOIN | ไม่มีโครงบังคับ ต้องจัดการเอง |
| ความถูกต้องของข้อมูล | constraint ปฏิเสธข้อมูลผิดได้ | ขึ้นกับโค้ดที่เขียน |

ไม่มีแบบใดดีกว่าเสมอ ต้องเลือกตามลักษณะของข้อมูล:
- ข้อมูลมีโครงชัดและมีความสัมพันธ์ → SQL
- ข้อมูลไม่มีโครงตายตัวและแต่ละรายการต่างกันมาก (เช่น log, เอกสารหลากหลาย) → NoSQL

## 2. ทำไมระบบของฉันเลือก SQLite

ข้อมูลในระบบ Campus Service ([ปรับให้ตรงกับระบบของคุณ]) ประกอบด้วยตาราง `users` และ `requests`

| ลักษณะข้อมูลของฉัน | SQL ตอบโจทย์เพราะ |
|---|---|
| ทุกคำร้องมี field เหมือนกัน (`status`, `priority`, ...) | schema บังคับโครงได้ |
| คำร้องชี้ไปหาผู้ใช้ผ่าน `requester_id` | foreign key + JOIN ดึงชื่อผู้แจ้งได้ในคำสั่งเดียว |
| ต้องการให้ข้อมูลถูกต้อง | constraint ปฏิเสธข้อมูลผิด และ API ตอบ 400 แทน 500 |

เหตุผลอื่น:
- ใช้ `node:sqlite` ที่มากับ Node ไม่ต้องติดตั้งเซิร์ฟเวอร์ฐานข้อมูลเพิ่ม
- ใช้ parameterized query เพื่อป้องกัน SQL injection
- [เพิ่มเหตุผลของตัวเอง เช่น ปัญหาที่เจอตอนทำ LAB 9–10]

**ข้อจำกัดที่รู้:** บน cloud free tier (เช่น Render) ไฟล์ระบบเป็นแบบชั่วคราว ข้อมูลใน `campus.db` ที่ผู้ใช้เพิ่มจะหายเมื่อ restart หรือ redeploy ระบบจริงจึงต้องเก็บข้อมูลในฐานข้อมูลที่แยกเครื่องกับ API

## 3. sync กับ async

| | sync | async |
|---|---|---|
| ตัวอย่าง | SQLite (`db.prepare(sql).all()`) | MongoDB Atlas (`await collection.find().toArray()`) |
| ฐานข้อมูลอยู่ที่ไหน | ไฟล์ในเครื่องเดียวกัน | คนละเครื่อง ต้องส่งคำขอผ่านเครือข่าย |
| การรอ | ได้ผลทันที ไม่ต้อง `await` | ต้องรอเครือข่าย จึงต้อง `await` (ระหว่างรอโปรแกรมทำอย่างอื่นได้ ไม่ค้าง) |

## 4. ถ้าเปลี่ยนไปใช้ MongoDB จะกระทบชั้นไหน

| ชั้น | กระทบไหม | เหตุผล |
|---|---|---|
| frontend | ไม่กระทบ | ยังเรียก API เดิม ไม่รู้ว่าข้อมูลมาจากไหน |
| service | **กระทบ** | ต้องเขียนใหม่ให้ใช้ MongoDB |
| controller | **กระทบ** | service เปลี่ยนจาก sync เป็น async ต้องเติม `await` |

ครั้งนี้กระทบ 2 ชั้น ต่างจากการเปลี่ยนแหล่งข้อมูลครั้งก่อน (localStorage, ไฟล์ JSON, SQLite) ที่แก้ชั้นเดียว เพราะเป็นการเปลี่ยน "สัญญา" ของ service จาก sync เป็น async ผู้เรียกจึงต้องปรับตาม

**สิ่งที่กำหนดว่ากระทบกี่ชั้นคือ sync หรือ async ไม่ใช่ SQL หรือ NoSQL**

| เปลี่ยนไปใช้ | ไลบรารี | กระทบ |
|---|---|---|
| Turso | `libsql` (sync) | service ชั้นเดียว |
| Turso | `@libsql/client` (async) | service + controller |
| Postgres (Neon, Supabase) | `pg` (async) | service + controller |
| MongoDB Atlas | `mongodb` (async) | service + controller |

สรุป: การแยกชั้นช่วยให้เปลี่ยนแหล่งข้อมูลได้ง่ายมาก แต่ถ้าเปลี่ยนสัญญาของชั้นหนึ่ง ผู้เรียกชั้นนั้นก็ต้องแก้ตามเสมอ
